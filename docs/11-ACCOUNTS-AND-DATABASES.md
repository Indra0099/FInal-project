# Accounts and personal databases — step by step

## 1. Start the updated application

Install Docker Desktop (or Docker Engine with Compose v2). Start Docker and open a terminal inside the project folder. The complete prerequisites are in [Local setup](05-LOCAL-SETUP.md).

macOS/Linux:
```sh
sh scripts/start.sh
```
Windows PowerShell:
```powershell
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

The helpers create `.env` only when missing, wait for PostgreSQL, configure the restricted workspace database role, and rebuild/start the application. Existing volumes and uploaded files are preserved. Fresh volumes also initialize the role through `infra/enable-workspaces.sh`. Flyway adds account and workspace metadata during backend startup.

On the original development Mac, use the dedicated Docker context:
```sh
DOCKER_CONTEXT=colima-shardquery sh scripts/start.sh
```
Other computers normally use their current Docker Desktop context; they do not need this profile.

## 2. Register and sign in

1. Open **http://localhost:8087**.
2. Choose **Create an account**.
3. Enter your name, email and a password of at least 12 characters (maximum 72 UTF-8 bytes).
4. Choose **Create account**. You are signed in automatically.
5. Use **Sign out** in the top bar. Return using your email and password.

No invitation token, default account or Gemini key is required for registration. Email addresses are normalized to lowercase. Email ownership verification, password reset and account deletion are not implemented in this local college demonstration. Use a password you can remember and do not reuse a sensitive account password.

Passwords are BCrypt hashes in PostgreSQL. Browser sessions use HttpOnly, SameSite=Strict cookies and expire after eight idle hours. Sessions are in backend memory, so restarting the application signs everyone out; accounts and data remain. Passwords and session tokens are never stored in browser localStorage.

## 3. Create a database

1. Open **My databases**.
2. Enter a name such as **College records**.
3. Click **Create database**.
4. Wait for it to appear in the database list.

This creates a real PostgreSQL database on the product PostgreSQL instance. Its internal name is generated by the server. The friendly name is stored in application metadata. This feature does not create an additional Docker container or a new distributed cluster. You can create up to three databases per account.

If provisioning fails, the database is marked Failed. Restore the service/role using the startup helper and click **Retry creation**. Do not delete Docker volumes to repair a role or password mismatch.

## 4. Define a table

Select a database and click **New table**. For an example table named **Students**, add:

| Column name | Type | Required |
| --- | --- | --- |
| student_name | TEXT | Yes |
| marks | INTEGER | Yes |
| enrolled_on | DATE | No |
| active | BOOLEAN | No |

Click **Create table**. An automatic `_row_id` identifies each record. Column names start with a lowercase letter and may contain lowercase letters, numbers and underscores. Database/table display names start with a letter and can contain spaces, numbers, hyphens and underscores.

Supported types:

- TEXT: at most 4,000 characters.
- INTEGER: PostgreSQL signed 64-bit integer. Values are returned as strings to preserve large-number precision in JavaScript.
- DECIMAL: up to 14 integer digits and four decimal places, returned as strings to preserve precision.
- BOOLEAN: true or false.
- DATE: a calendar date, stored without a time zone; API format is `YYYY-MM-DD`.

Each database supports 12 tables; each table supports 20 user-defined columns. Schema editing, table/database deletion, CSV import, custom constraints, foreign keys and arbitrary SQL are outside this first editor version.

## 5. Add and edit records

1. Select the Students table.
2. Click **Add row**.
3. Enter a fictional student, for example Asha, marks 92, and an enrollment date.
4. Click **Save record**.
5. Add another student with marks 65.
6. Use **Edit** beside a record to change its values and save.

Empty optional fields become SQL NULL. Required fields and data types are validated on the server. The editor shows 50 records per page; use Previous/Next for larger tables. A table holds up to 1,000 records in this bounded demonstration. Add/edit writes use bound SQL parameters. Creating tables and entering records do not require an AI key.

## 6. Ask questions about your table

1. Click **Ask about this table**, or choose the table under **Query data source** in Query workspace.
2. Keep **Database** mode selected.
3. Ask: **Show students with marks above 80, sorted by marks from highest to lowest.**
4. Click **Run query**.
5. Inspect Answer, Records and How this query ran.

The backend sends the selected column definitions and question to Gemini for a structured filter plan. It validates column names, operators, types, sort order and limits before compiling a parameterized SELECT. Gemini never executes free-form SQL. At most five AND filters and 100 returned records are allowed. Operators are equals, greater/less than (inclusive variants), and text contains. It then summarizes the retrieved records through Gemini.

An explicitly selected table supports row filtering and sorting. Choose **Automatically choose** or **My databases — all tables** to let the planner select and join up to two related tables, including tables in different personal databases. Aggregates, outer joins, data changes through chat and personal-table RAG associations are not implemented. Unsupported requests receive an explanation. The sample commerce source remains available for the separate commerce and hybrid-document demonstration. See [personal database routing](12-PERSONAL-QUERY-ROUTING.md) for the student/fee example. Personal-table queries bypass the answer cache so row edits are reflected on the next query.

AI features continue using the configured Gemini provider. No OpenAI fallback is added. Relevant schema/record/document content is sent to Gemini when AI is used. Use fictional data for a college demonstration. Without a key, table creation and the data editor still work.

## 7. Privacy and existing data

Each signed-in account can access only its own databases, tables, documents and query history. The server validates ownership on reads, downloads, retries and writes. Background query jobs retain the submitting user's ID; retrieval accepts only that user's ready document IDs. Document deduplication and answer-cache keys include account ownership. Requests for another account's resource return 404.

Sample commerce databases are shared fictional, read-only data. They are deliberately available to every account. All personal databases are owned at PostgreSQL level by the restricted application workspace role; account isolation is enforced by backend ownership checks. This is not separate PostgreSQL login isolation per user, and a machine/database administrator can access installation data.

On upgrading an earlier anonymous installation, existing documents and query history are preserved with `user_id = NULL`. They are hidden from new accounts and are never automatically assigned to the first registrant. To use sample documents, upload them after signing in. An installation administrator can explicitly migrate identified legacy records after verifying ownership; the public API cannot claim them.

## 8. Implementation walkthrough

1. **Migration:** `V1__accounts_and_user_databases.sql` creates users and database/table metadata, then adds nullable owner IDs to legacy documents/jobs. The original initialization schema is Flyway baseline version 0.
2. **Authentication:** `auth/AuthService` hashes passwords; `AuthController` registers, signs in and returns the current account. `SecurityConfig` protects APIs, rotates session identifiers and enforces CSRF. `LocalGuard` limits writes and sign-in attempts.
3. **Data ownership:** repository queries scope documents/jobs by account. Worker jobs keep ownership in persisted metadata. Existing anonymous data is not automatically visible.
4. **Database provisioning:** `WorkspaceService` creates UUID-named databases using `shard_workspace`, which has CREATEDB but no superuser/role-administration privileges. Public connection access is revoked on personal databases. Metadata records READY/FAILED status and supports retry.
5. **Table/record operations:** validated column definitions become whitelisted PostgreSQL types. Server-generated physical names and quoted identifiers prevent SQL identifier injection. Row values and query filters use PreparedStatement parameters. JDBC connections close after each bounded operation.
6. **AI queries:** `GeminiGateway.tablePlan` produces a bounded plan. `WorkspaceService` verifies it and executes a read-only transaction. `QueryService` stores the result in the user's history.
7. **Frontend:** `Auth.jsx` gates the workspace and manages login/logout. `api.js` keeps CSRF tokens in memory. `DatabaseStudio.jsx` provides database/table/row forms. App's query selector passes a table UUID. UI requests include the session cookie automatically.
8. **Verification:** JUnit runs real database operations, account/session requests and ownership rejection. Automated AI integration uses an explicitly labelled local HTTP fixture; live demonstrations use Gemini. See [verification evidence](VERIFICATION.md).

Metadata and a physical personal database are separate PostgreSQL transactions. This local single-instance implementation cannot promise atomic provisioning across an application/process crash; failed database creation can be retried. Backups must include the full product PostgreSQL volume (or every personal database), metadata, uploads and relevant vector data. Public deployment and multiple backend instances require further work, including HTTPS, shared session/worker coordination and operational backups.
